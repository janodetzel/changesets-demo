THE RULES BEHIND THE SCENARIOS

Why does a preparation merge not redeploy DEV?

Feature merges belong to deploy-dev.yml. A version-preparation merge belongs to release.yml, which builds from that exact commit without a DEV deployment. The versioned candidate is a new build. Its local bundle checks do not prove deployment on DEV; final acceptance happens on STAGE. DEV can keep advancing independently.

What is frozen, and when?

The preparation PR is a mutable proposal. Its merge SHA freezes the candidate source. A build produces an immutable artifact ID and digest. STAGE and PROD download that same artifact. New commits on main do not change it. Refresh a preparation PR before merging if integration has advanced; review the resulting contents, not an old description.

What do Nx, paths, and GitHub Environments each do?

Nx Release calculates versions, consumes version plans, and generates changelogs. The demo uses dorny/paths-filter, not Nx affected, to select integration domains. GitHub Environments supply approval boundaries and deployment history. They do not select source changes or make APIs compatible. stage-billing and stage-payment may target separate stacks in the same physical STAGE account.

Can I release feature 3 without broken feature 2 in the same domain?

Not from an artifact containing both. Version plans are descriptions, not switches that exclude code. Fix or revert feature 2, promote an older safe candidate, or explicitly assemble and retest a selective release branch. Independent domain releases do not provide independent feature releases inside a domain.

Does another minor feature always mean another minor version?

No. Two compatible additions can join the active 1.1.0 target in its next RC. After 1.1.0 is finalized, a later minor feature targets 1.2.0-rc.1. Candidate counters reset for each target, with committed history and tags preventing reuse of previously reserved numbers. Release tooling can trigger builds without affecting application SemVer.

What if STAGE has an integration failure between domains?

Hold the affected candidates. Prefer backward-compatible provider changes so the provider can release first, followed by consumers. If they genuinely need a coordinated rollout, document and test it. The demo services have no runtime dependencies; their passing tests do not establish compatibility for actual EMP services.

What complexity would RC versions add?

Track the last stable release separately from an active target, aggregate changes across attempts, serialize preparation and finalization, generate cumulative notes, and bind a stable release to an accepted artifact. Frozen scope and parallel backports add more work. Nx supplies version primitives; it does not automatically manage this entire lifecycle.

Where do I find the real workflow and release records?
  • Deploy DEV selects and deploys changed integration domains.
  • Prepare semantic releases maintains the version PR.
  • Release domains starts versioned candidates.
  • Domain release keeps STAGE and PROD on the same artifact.
  • GitHub Actions and GitHub Releases contain actual results.
