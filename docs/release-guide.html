NATIVE NX · INDEPENDENT DOMAIN RELEASES

One integration branch.
Separate release decisions.

Follow code into DEV, freeze a versioned artifact, then approve that artifact through STAGE and PROD. See why DEV can move ahead, why versions may be skipped, and why the release notes must start at the last successful production deployment.

This self-contained guide explains the current stable-SemVer design. All versions, commits, and artifact names below are fictional. It reads no live state and starts no deployments. Formal RC versions and the earlier custom RC engine have been removed.

BOUNDARIES AND TRADEOFFS

Why build and deploy only after merging the preparation PR?

The merge gives the candidate a fixed source commit and reserves its version before building. STAGE and PROD then use one immutable artifact in the same workflow run, without transferring validation between a changing PR and a later merge. DEV continues independently. The tradeoff: merging approves release preparation, not production readiness. STAGE testing and the separate PROD approval establish that afterwards.

How do multiple PRs determine a version?

Nx analyzes Conventional Commits since the previous version tag. Several minor and patch changes prepared together produce one minor bump. If a minor version was already reserved, a later minor feature gets a new minor version. No custom active-target or RC lifecycle exists.

Can one domain release while another waits?

Yes. Nx affected selects integration projects and consumers. Changed versions select release builds. GitHub's domain-specific STAGE and PROD approvals are independent. They are logical approval boundaries and can target stacks in the same physical AWS account.

What if the production baseline changes after the notes are generated?

The candidate includes the comparison baseline in its checksummed metadata. Production verifies it again before deployment. A different baseline stops promotion so the candidate's notes and evidence can be reviewed again. A retry for the same source/version already deployed is allowed. This is workflow bookkeeping, not continuous runtime inventory.

Can I release features 1 and 3 without broken feature 2?

Not from a domain artifact containing all three. Versioning cannot exclude code. Fix or revert the defect, promote an older safe artifact, or assemble and retest an explicit selective release. Independent domain deployment is not arbitrary feature selection.

What happens during a rollback or partial deployment?

A recorded successful deployment of an earlier version becomes the comparison baseline. Failed or in-progress attempts do not replace it. A physical deployment that changes infrastructure before failing can differ from the recorded baseline; reconcile that state explicitly. The demo does not simulate database recovery or partial infrastructure changes.

Why is package publishing not gated by STAGE or PROD?

Registry versions are immutable and opt-in: consumers choose when to upgrade, while deployments change shared environments. Publishing at the release decision lets consumers build against a new contract before the matching service reaches production, which expand/contract compatibility requires. What is actually running remains the deployment record's question, never the registry's. For pre-release iteration, snapshots (0.0.0-snapshot.sha under the snapshot dist-tag) publish for Nx-affected packages on every integration merge and never satisfy a caret range.

What happened to formal release candidates?

The versioned build is still a candidate for deployment, but its version has no rc suffix. We accept gaps in production versions to avoid custom target tracking, prerelease finalization, and a shipped-change ledger. Native Nx manages ordinary SemVer and changelogs.
